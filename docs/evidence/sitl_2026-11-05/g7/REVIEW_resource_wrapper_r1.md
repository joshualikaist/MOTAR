# Resource wrapper source review r1

Reviewer: Codex `/root/g7_guard_review`; model GPT-6 (Codex; exact serving variant not exposed). Source-only audit of external `run_capped.py` and supplied `cap_validation.json`. No tests, GPU, repository edits, or Beads actions performed.

Verdict: **HOLD for unattended process-tree cleanup; basic single-process RSS/time watchdog behavior is supported by the supplied probes.** This is an operational sampled RSS bound, not a kernel memory hard cap. No scientific result assessed.

Findings:

1. **High — termination can leave descendant compute alive.** `stop()` signals only the frozen `known` map (lines 33–43). A process can fork after the last sample or from its SIGTERM handler; no descendant discovery occurs during the one-second TERM grace or before KILL. The session established by Popen is never signaled as a group. Consequently the wrapper may return while a new descendant remains alive. Refresh descendants of every identity-verified observed process during cleanup, and include process-group cleanup for the launch session as a fallback; verify cleanup completion before reporting successful shutdown. An escaping/orphaned process must produce an explicit failed-cleanup result.
2. **Medium — ancestry discovery can lose a live subtree.** Each sample follows ancestry only from `child.pid` (line 54). Observed descendants remain accounted after reparenting, which is useful, but newly born descendants of those reparented processes are not discovered. A short-lived intermediary can also fork and exit entirely between samples. A subreaper plus discovery from the wrapper's own process tree can improve coverage; otherwise explicitly constrain the operational guarantee to observed descendants, and use the launcher/session structure to make cleanup reliable. PID/start-time identity checks correctly reduce PID-reuse risk for already-observed processes.
3. **Medium — abnormal cleanup may erase the operational receipt.** `child.wait(timeout=10)` can raise; Popen/snapshot exceptions also propagate before the CLI writes its report. A child missed in the initial snapshot leaves `known` empty, so `stop(known)` cannot kill it. Write a failed wrapper receipt in an outer finally/exception path and retain a direct child/process-group fallback independent of discovery.
4. **Probe limitation.** All three supplied probes observed exactly one process. They support positive completion, RSS rejection, and elapsed-time rejection, but do not validate descendant aggregation, lingering-child cleanup, TERM-to-KILL escalation, or detached descendants. The RSS negative uses a 2 MiB limit below the positive Python process's approximately 8 MiB baseline, so it does not establish acceptance of an under-limit process at the same threshold. Add same-threshold positive/allocation-negative controls and an aggregate multi-child positive/negative plus a TERM-handler-fork cleanup probe before relying on the stronger process-tree claim.

Correct and useful aspects: Linux /proc stat indices for ppid/starttime/RSS are correct; aggregate RSS intentionally counts shared pages separately; timeout uses monotonic time; sampled peak and nonzero sample count are recorded; positive and rejected probes are distinguished; nonzero child exits and stop reasons yield wrapper exit 1; report refuses overwrite. At 0.25 s polling, allocation overshoot and unobserved transient peaks remain inherent limits even after cleanup repairs. A 12 GiB threshold therefore must not be described as an enforced kernel cap.

## G1-B/C — vehicle state is 3D, policy authority is planar

`navrl_task.py:transform_action_to_command:4953-5008` clips action XY per axis, applies the riskcap filter, overwrites command Z with

`I <- clamp(I + (1-z)*0.1, -2.5, 2.5)`

`v_z_cmd = clamp(4*(1-z) + I, -2.5, 2.5)`.

The actor's third output cannot select altitude. At `step:5051-5057`, raw clipped action Z is still retained in `prev_action` for checkpoint compatibility, whereas only XY is replaced by governed XY. This is a documented, frozen proprioceptive-history limitation, not a new GT leak. Describing the previous-action vector as entirely executed physical commands would be inaccurate.

Yaw is a requested Euler yaw rate, transformed using current Euler attitude to desired body rates (`velocity_control.py:LeeVelocityController.update:87-95`; `base_lee_controller.py:euler_rates_to_body_rates:193`). Roll/pitch are emergent attitude response to the required translational force, not separate actor channels. The Lee force is `(K_v*(v_cmd_world-v_world)-gravity)*mass`; fixed midpoint K_v=2.5/s, K_rot=[1,1,0.5], K_angvel=[0.15,0.15,0.15] follow `base_lee_controller.py:init_tensors:34-62` and shared `lee_controller_config.py:22-52`, with `randomize_params=False`.

`velocity_control.py:update:34-53` bounds the desired force direction to 45 deg. It does not clamp actual quaternion. Tilt-compensation uses `T=f_z/b3_z` only while current body-z projection exceeds 0.5; otherwise it falls back to force projection (`:55-80`). Motor saturation, attitude lag, contact and inherited initial angular velocity remain dynamic. The controller is reevaluated each physics step; the 100 ms action/altitude-loop request is held during the ten inner steps (`env_manager.py:step:444-476`, `pre_physics_step:358-371`; `robot_manager.py:pre_physics_step:486-489`; `base_multirotor.py:step:296-308`).

## G1-E — active motor RK4 defect, with the discrete-gain caveat

This is an active path, not unused generic code. `robots/__init__.py:40` registers `navrl_quad` as BaseMultirotor + NavRLQuadCfg. `navrl_quad_config.py:10-49` inherits BaseQuadCfg and overrides asset/init/sensor only. `base_quad_config.py:control_allocator_config:159-194` sets motor-link forces, four motors, use_rps=True, tau up/down=0.04 s, thrust [0,2] N each, max_rate=100000 and use_discrete_approximation=True; no integration_scheme override. `base_multirotor.py:init_tensors:121` constructs ControlAllocator with measured physics dt; `control_allocation.py:ControlAllocator.__init__:43` constructs MotorModel. `motor_model.py:17` defaults scheme to rk4, `:91-119` selects RPM RK4, `:211-219` calls `rk4_integration`.

For constant reference r, physical first-order lag y'=k(r-y), e=r-y, classical RK4 requires k2=k*(e-dt*k1/2), k3=k*(e-dt*k2/2), k4=k*(e-dt*k3). Active `motor_model.py:rk4_integration:169-175` instead uses plus for these intermediate errors while adding the result positively to current RPM. Without rate clipping, its increment is `e*(h+h²/2+h³/6+h⁴/24)`, h=k*dt. Correct RK4 for the same supplied ODE coefficient gives `e*(h-h²/2+h³/6-h⁴/24)`. This is a direct mathematical counterexample to the RK4 name.

Current `discrete_mixing_factor:178-180` additionally transforms coefficient to k=1/(dt+tau)=20/s, not nominal 1/tau=25/s. At dt=.01,tau=.04, h=.2: production increment fraction .2214; correct RK4 for supplied k is .181266667; exact supplied-k response .181269247. **Do not report the 22% same-coefficient difference as a 22% physical motor error:** nominal tau=.04 exact gain is .221199217, only ~0.091% below production, whose effective fixed-step tau is .0399588 s. The two departures accidentally nearly cancel at this fixed ratio. It could alternatively be treated as an undocumented discrete response, which must then be named and qualified as such rather than “RK4 first-order lag.”

Counterexample outside OCC's fixed step (proposal, never executed in simulator): dt=.1,tau=.04 -> production gain 1.0409725, overshooting a positive first-order reference from zero, whereas exact nominal tau gives .917915. A timestep change would also alter this plant. The 100000 max-rate limit is inactive in the normalized example and in a 0->2 N step with the declared thrust coefficients; RPM fractions are squared when mapped to thrust. No actual per-motor time history was recorded to fit the effective response or quantify closed-loop outcome sensitivity. Never patch historical plant bytes or retroactively label old results invalid solely from this algebra; any remedy is a new plant lineage.

## G1-G — layouts and passability

Full-height bars are upright/unrotated; actual stored layout quaternions are [0,0,0,1]. bars_h3 source has same collision/visual box dimensions. `env_object_config.py:bar_asset_params:793-860` sets full-height pool and z-ratio .5. Actual raw layouts were sampled deterministically for **env0/episode0 in each of 112 cells**, independently using pairwise AABB separation, not the production placement routine. All sample heights are 3 m and z-span 0..3. 102/112 samples contain touching/overlapping bar pairs, consistent with intentional compound-wall placement, not itself a physics defect; minimum separate-pair Euclidean surface gap in these samples is .591925 m. No sample alone proves the full 93,092-layout population or global free-space connectivity.

The navrl_band rule is centre distance <=.4 or >=1.6, with saturation merging (`asset_manager.py:_navrl_band_xy_spacing:346-432`). For two maximum .8 m squares diagonally separated by 1.6 m, surface corner gap can be 1.6-.8*sqrt(2)=.468629 m. Centre spacing is not a clearance guarantee for an attitude-varying robot or its tracking envelope. The source itself acknowledges this. Local general spawn clearance uses a conservative legacy arm-plus-5-inch-prop circumradius plus .45 tracking reserve (`navrl_task.py:_robot_spawn_inflation_radius_m:2296-2338`, `_spawn_required_surface_margin_m:2341`, `_randomize_general_drone_spawn:2353-2414`): (.13+.0635)*sqrt(2)+.45=.723650 m from each bar surface. That differs deliberately from the .197990 m body collision circumradius. The clear initial camera-centre LOS and 10 m target range do not prove a safe swept-body route or a feasible recovery trajectory. OCC runs target_route_mode=off, so optional route planners do not qualify these layouts.

No global no-path fraction, narrow-passage distribution under the actual support/attitude reserve, viable braking tube, or mutual start-target reachability test is in the OCC acceptance record. Qualification should distinguish physically passable body, reserve-passable tracking corridor, and kinematically/dynamically reachable route; a single point grid or centre ray cannot substitute for all three.
